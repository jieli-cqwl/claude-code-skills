# /api-spec -- 接口规格定义与生成

> 引用者：pipeline-designer（通过 skills 字段加载）、用户直接调用

---

## 1. 接口定义完整性标准

每个接口必须完整定义以下内容：

**入参规范**：
- 参数名称和类型
- 参数校验规则（长度、范围、格式、必填/可选）
- 校验失败的错误响应

**出参规范**：
- 成功响应格式和字段
- 失败响应格式和错误码
- 边界情况的响应

**错误码体系**：
- 每个接口至少定义：参数校验错误、业务逻辑错误、系统错误
- 错误码命名有统一前缀或分类
- 错误消息面向用户（不暴露技术细节）

---

## 2. 接口定义分档

按接口规模选择定义方式，避免小需求过度文档化、大需求定义不足：

| 档位 | 触发条件 | 接口定义方式 |
|------|---------|------------|
| 精简版 | 接口 ≤3 且非全栈 | 内联在 handoff_design.md，使用简化表格 |
| 标准版 | 接口 4-10 | handoff_design.md 的"接口规格"专节，使用结构化模板 |
| 增强版 | 接口 >10 或需对外暴露 API | 输出独立的 `design/API-SPEC.md`，使用结构化模板 |

---

## 3. 结构化接口模板（标准版/增强版共用）

```markdown
### {METHOD} {PATH}

**描述**: {一句话说明}

**入参**:

| 字段 | 类型 | 必填 | 校验规则 | 说明 |
|------|------|------|---------|------|

**出参（成功 {STATUS_CODE}）**:
```json
{ "结构化示例" }
```

**错误码**:

| HTTP 状态码 | error_code | 触发条件 | 用户消息 key |
|------------|------------|---------|-------------|

**边界行为**:

| 场景 | 预期行为 |
|------|---------|
```

---

## 4. 精简版接口表格

接口 ≤3 且非全栈时，使用如下简化表格内联在 handoff_design.md 的"接口清单"中：

```markdown
| 接口 | 入参 | 出参 | 关键错误码 |
|------|------|------|-----------|
| POST /api/v1/users | {name: str, email: str} | 201 {id, name, email} | 409 DUPLICATE_EMAIL |
```

## 6. 独立使用：执行流程

> **仅用户直接调用 `/api-spec` 时适用，被 agent skills 注入时忽略此节。**

支持两种输入模式：
- **A) 逆向模式**：从已有代码（路由/Controller）扫描提取接口，补全规格文档
- **B) 正向模式**：从需求文档或口头描述，设计接口规格

### 6.1 输入识别（自动判断模式）

| 输入类型 | 模式 |
|---------|------|
| 参数是代码目录/文件 | 逆向模式 |
| 参数是需求文档 | 正向模式 |
| 参数是文字描述 | 正向模式 |
| 无参数 | 提示用户提供输入 |

### 6.2 扫描与分析

**逆向模式**：
1. Glob/Grep 搜索路由定义（`@app.route`、`@router`、`@GetMapping`、`app.get` 等）
2. Read 读取路由处理函数
3. LSP 语义分析：`goToDefinition` 追踪请求/响应模型，`findReferences` 确认调用关系

**正向模式**：
1. Read 需求文档
2. 提取接口需求（动作 + 资源 + 约束）
3. 根据业务领域设计 RESTful 接口

### 6.3 自动选档 + 按模板生成接口规格

根据识别到的接口数量自动选择档位（第 2 节），按对应模板（第 3 或 4 节）生成接口规格文档。

### 6.4 合规检查

Read `~/.claude/reference/REST接口规范.md`，确保生成的接口规格符合以下要求：
- 路径命名规范
- HTTP 方法语义正确
- 状态码选择合理
- 错误响应格式统一

### 6.5 完整性检查清单

生成完成后逐条确认：

1. [ ] 每个接口都定义了入参（字段、类型、校验规则）？
2. [ ] 每个接口都定义了成功响应和失败响应？
3. [ ] 每个接口至少定义了参数校验错误、业务逻辑错误两类错误码？
4. [ ] 错误消息面向用户，未暴露技术细节？
5. [ ] 边界行为已定义（空值、极限值、并发场景）？
6. [ ] 接口路径、方法、状态码符合 REST 规范？

---

## 7. 约束

- Do NOT 生成实现代码，只输出接口规格文档
- Do NOT 遗漏错误场景，每个接口必须定义成功和失败两种路径
- Do NOT 使用模糊描述（如"返回用户信息"），必须列出具体字段和类型
- Do NOT 在精简版中省略关键错误码
