# QA Methodology - QA 验收方法论

> 引用者：pipeline-qa（主用）

---

## 1. 验收标准唯一来源原则

QA 验收的唯一标准是 `handoff_clarify.md`，不是 Plan，不是 Design，不是代码。

### 为什么

- clarify 定义了**用户真正要什么**
- Plan/Design 是实现路径，可能偏离需求
- 代码通过测试不等于满足需求（"代码正确" != "功能正确"）

### 信息来源分工

| 文件 | 用途 | 是否作为验收标准 |
|------|------|----------------|
| handoff_clarify.md | 验收标准（规则+正例+反例+排除项） | 是（唯一标准） |
| handoff_design.md | 获取接口路径、参数格式 | 否（仅获取技术信息） |
| handoff_run.md | 不读取 | 否（保证独立性） |
| handoff_check.md | 不读取 | 否（保证独立性） |

---

## 2. 与 Check 的差异化

QA 和 Check 有明确的分工，禁止重复工作。

| 维度 | Check 负责 | QA 负责 |
|------|-----------|---------|
| 目标 | 代码质量 | 功能是否满足需求 |
| 标准 | 测试/Lint/类型/代码规则/AC | clarify 规则+正例+反例 |
| 视角 | 开发者视角（代码正确吗） | 用户视角（功能对吗） |
| 方法 | 静态分析+运行测试 | 端到端功能验证 |

### QA 禁止做的事

- 重复跑 Lint/类型检查（Check 已做）
- 重复运行单元测试（Check 已做）
- 检查代码风格/结构（Check 的职责）
- 阅读代码实现细节（保持黑盒视角）

## 3. 逐条需求覆盖方法

每条 clarify 规则及其正例/反例，必须逐条验证并记录结果。

### 验收表格式

```markdown
| # | clarify 规则 | 验证类型 | 期望结果 | 实际结果 | 状态 | 验证方式 |
|---|-------------|---------|---------|---------|------|---------|
| R1 | 用户名 3-20 字符 | 正例 | "alice" -> 201 | "alice" -> 201 | PASS | curl POST |
| R1 | 用户名 3-20 字符 | 反例 | "ab" -> 422 | "ab" -> 422 | PASS | curl POST |
| R1 | 用户名 3-20 字符 | 边界 | "abc"(3字符) -> 201 | "abc" -> 201 | PASS | curl POST |
| R2 | 密码>=8字符 | 正例 | "12345678" -> 201 | "12345678" -> 201 | PASS | curl POST |
| R2 | 密码>=8字符 | 反例 | "1234567" -> 422 | "1234567" -> 500 | FAIL | curl POST |
| E1 | 排除：头像上传 | 排除 | 无此功能 | 无此接口 | PASS | 接口不存在 |
```

### 每条规则的验证覆盖

- **正例**：至少 1 个（clarify 中给出的正例）
- **反例**：至少 1 个（clarify 中给出的反例）
- **边界**：至少 1 个（边界值）
- **排除项**：确认未实现

## 4. 端到端验证方法

QA 从用户使用角度进行端到端验证，不看代码实现。

### 验证流程

```
启动真实服务 -> 健康检查 -> 端到端测试 -> 停止服务
```

### 详细步骤

1. **启动服务**：使用项目标准启动命令
2. **健康检查**：确认服务正常响应
3. **逐条验证**：按验收表逐条执行测试
4. **边界测试**：测试 clarify 中提到的边界条件
5. **排除项验证**：确认排除项未实现
6. **停止服务**：清理测试环境

### 如果无法启动服务

某些项目（CLI 工具、库等）不需要启动服务：
- CLI 工具：直接运行命令验证
- 库/SDK：编写调用脚本验证
- 数据处理：准备测试数据运行验证

## 5. FAIL 项三要素

每个 FAIL 项必须包含三个要素，缺一不可：

### 格式

```markdown
### FAIL: [规则编号] [规则描述]

**期望行为**: [clarify 中定义的预期结果]
**实际行为**: [实际观察到的结果]
**复现命令**:
```bash
curl -X POST http://localhost:8000/api/v1/users \
  -H "Content-Type: application/json" \
  -d '{"username": "ab", "password": "12345678"}'
# 期望: 422 {"error_code": "VALIDATION_ERROR"}
# 实际: 500 Internal Server Error
```
```

### 三要素缺一不可

| 要素 | 必须包含 | 不合格示例 |
|------|---------|-----------|
| 期望行为 | clarify 中的具体规则定义 | "应该报错" |
| 实际行为 | 实际观察到的具体结果 | "没有正常工作" |
| 复现命令 | 可直接运行的完整命令 | "调用接口会失败" |

## 6. Few-shot 对比示例

### 好的 QA 输出

```
输入分析：
- clarify 定义 F1 用户注册功能，3 条规则 + 2 个排除项
- 从 design 获取接口路径：POST /api/v1/users

验收决策：
- 以 clarify 为唯一标准，独立端到端验证
- 启动服务 -> 逐条验证 -> 停止服务

验收表：
| # | 规则 | 类型 | 期望 | 实际 | 状态 |
|---|------|------|------|------|------|
| R1 | 用户名3-20字符 | 正例 | "alice"->201 | 201 | PASS |
| R1 | 用户名3-20字符 | 反例 | "ab"->422 | 422 | PASS |
| R2 | 密码>=8字符 | 正例 | "12345678"->201 | 201 | PASS |
| R2 | 密码>=8字符 | 反例 | "1234567"->422 | 500 | FAIL |
| R3 | 邮箱唯一 | 反例 | 重复->409 | 409 | PASS |
| E1 | 排除头像上传 | 排除 | 无此接口 | 无 | PASS |

FAIL 详情：
### FAIL: R2 密码>=8字符
期望行为: 密码"1234567"(7字符) -> 422 VALIDATION_ERROR
实际行为: 500 Internal Server Error
复现命令:
  curl -X POST localhost:8000/api/v1/users \
    -d '{"username":"test","password":"1234567","email":"t@t.com"}'

RESULT: FAIL（1/5 规则验证未通过）
```

### 坏的 QA 输出

```
测试全部通过，功能正常。PASS
（没有逐条验收、没有端到端验证、没有正例/反例/边界测试）
```

## 7. 检查清单

QA 验收完成前必须确认：

1. [ ] 验收标准是否以 clarify 为唯一来源？（未参考 Plan/代码作为标准）
2. [ ] 是否逐条验证了 clarify 中的每条规则？
3. [ ] 每条规则是否覆盖了正例、反例、边界？
4. [ ] 排除项是否也进行了验证（确认未实现）？
5. [ ] FAIL 项是否包含三要素（期望/实际/复现命令）？
6. [ ] 是否进行了端到端验证（而非只看单元测试结果）？
7. [ ] 是否与 Check 做了差异化（未重复 Lint/测试/代码审查）？
8. [ ] 是否独立验证（未读取 handoff_run.md 或 handoff_check.md）？

## 8. 常见反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| 重复 Check | 又跑一遍测试和 Lint | 只做功能验证，不做代码质量检查 |
| 标准偏移 | 以 Plan/Design 为验收标准 | 只以 clarify 为验收标准 |
| 只验正常路径 | 不测边界和异常 | 正例+反例+边界全覆盖 |
| 信任上游 | Check 通过就等于功能正确 | 独立端到端验证 |
| 模糊 FAIL | "有些功能不太对" | FAIL 项三要素缺一不可 |
| 读代码判断 | 看代码逻辑推断功能正确 | 保持黑盒视角，运行验证 |
