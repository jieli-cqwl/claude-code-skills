# 产品需求分析方法论

> /prd Skill 的核心方法论参考。

---

## 1. 业务理解框架

需求分析不是"翻译用户的话"，而是"理解用户的业务问题"。

| 层次 | 问题 | 产出 |
|------|------|------|
| **Why** | 为什么需要这个功能？解决什么业务问题？ | 业务背景 |
| **Who** | 谁在用？什么场景？什么频率？ | 用户故事 |
| **What** | 具体做什么？不做什么？ | 功能需求 + 排除项 |
| **How** | 业务流程是什么？状态如何流转？ | 业务流程图 |

### 用户故事格式

```
作为 [角色]，
我希望 [动作/能力]，
这样 [业务价值/目的]。
```

每个核心功能至少一个用户故事。用户故事回答"为什么要做"，验收标准回答"怎么判断做对了"。

### 业务流程分析

复杂需求（> 3 个功能点）必须包含业务流程：

```
触发事件 → 步骤 1 → 决策点 → 步骤 2a/2b → 结束状态
```

流程分析的目的：
- 暴露隐含的状态转换
- 发现需求间的依赖关系
- 识别异常路径和边界条件

## 2. 需求挖掘技巧

### 追问路径

指导原则：第一性原理——剥离表面方案，回到根本问题。

- **现状追问**："目前你/用户是怎么处理这件事的？" → 挖掘现状和 workaround
- **痛点确认**："现在的方式有什么问题？" → 确认痛点真实存在
- **目标锚定**："你希望做了之后达到什么效果？" → 锚定成功标准
- **必要性评估**："如果不做，最坏会怎样？" → 评估优先级

### 核心思考框架

- **第一性原理**：剥离表面方案和已有假设，回到根本问题重新推导
- **5 Whys**：对每个需求至少追问一层"为什么"，直到触达根因——不是机械问 5 次
- **JTBD**：用户雇佣这个功能来完成什么任务？关注功能维度（完成什么）、情境维度（什么场景）、情感维度（什么驱动）
- **苏格拉底式提问**：不直接给判断，通过复述、追问、假设检验引导用户自己厘清需求

### 需警惕的信号

检测到以下信号时必须追问，不可跳过：

| 信号 | 追问方向 |
|------|---------|
| "竞品有这个功能" | 我们的用户也遇到同样的问题吗？ |
| "老板/客户说要做" | 他们遇到了什么具体问题？ |
| 用户直接描述方案而非问题 | 你希望这个方案解决什么问题？ |
| "应该很简单" | 你预期的具体行为是什么？ |

## 3. 语义拆解原则

当功能点 > 3 个或跨模块时，将需求拆解为独立的 UNIT 文件。

| 原则 | 说明 | 反例 |
|------|------|------|
| **语义闭环** | 每个 UNIT 独立可理解，不需要看其他 UNIT 才懂 | 把"创建"和"校验"拆到两个 UNIT |
| **最小完整** | 包含需求描述+验收标准+排除项，不多不少 | 只有描述没有验收标准 |
| **单一职责** | 一个 UNIT 对应一个功能点或紧密相关的功能点组 | 把所有 API 放一个 UNIT |
| **依赖最小** | 尽量减少 UNIT 间的依赖 | 每个 UNIT 都依赖其他 3 个 |

## 4. 排除项标准

好的排除项：
- "不做邮箱可达性验证" — 是合理需求但明确排除
- "不支持批量导入" — 是合理需求但明确排除

坏的排除项：
- "系统不应崩溃" — 否定句，不是排除项
- "不做非法操作" — 太模糊
