# 产品需求分析方法论

> /prd Skill 的核心方法论参考。

---

## 1. 产品经理思维框架

### 1.1 业务理解优先

需求分析不是"翻译用户的话"，而是"理解用户的业务问题"。

| 层次 | 问题 | 产出 |
|------|------|------|
| **Why** | 为什么需要这个功能？解决什么业务问题？ | 业务背景 |
| **Who** | 谁在用？什么场景？什么频率？ | 用户故事 |
| **What** | 具体做什么？不做什么？ | 功能规则 + 排除项 |
| **How** | 业务流程是什么？状态如何流转？ | 业务流程图 |

### 1.2 用户故事格式

```
作为 [角色]，
我希望 [动作/能力]，
这样 [业务价值/目的]。
```

每个核心功能至少一个用户故事。用户故事回答"为什么要做"，规则回答"怎么判断做对了"。

### 1.3 业务流程分析

复杂需求（> 3 条规则）必须包含业务流程：

```
触发事件 → 步骤 1 → 决策点 → 步骤 2a/2b → 结束状态
```

流程分析的目的：
- 暴露隐含的状态转换
- 发现规则间的依赖关系
- 识别异常路径和边界条件

## 2. 需求拆解方法论

### 2.1 语义拆解 vs 机械拆解

| 维度 | 语义拆解（/prd） | 机械拆解（context_gate.sh） |
|------|----------------|--------------------------|
| 拆分依据 | 业务规则的语义边界 | Token 数量阈值 |
| 完整性 | 每个 UNIT 是完整的业务闭环 | 可能切断规则 |
| 背景信息 | 每个 UNIT 含业务背景 | 无背景，纯文本片段 |
| 依赖关系 | 显式声明 UNIT 间依赖 | 无依赖信息 |
| 下游使用 | design/plan 可直接以 UNIT 为单位工作 | 需要重新理解上下文 |

### 2.2 何时拆解为 UNIT

| 条件 | 模式 | 产出 |
|------|------|------|
| 规则 ≤ 3 条，单模块 | 简单（内联） | master.md（规则内联） |
| 规则 > 3 条，或跨模块 | 复杂（拆解） | master.md + units/*.md |

### 2.3 UNIT 拆分原则

| 原则 | 说明 | 反例 |
|------|------|------|
| **语义闭环** | 每个 UNIT 独立可理解，不需要看其他 UNIT 才懂 | 把"创建"和"校验"拆到两个 UNIT |
| **最小完整** | 包含规则+正例+反例+边界，不多不少 | 只有规则没有示例 |
| **单一职责** | 一个 UNIT 对应一个业务规则或紧密相关的规则组 | 把所有 API 放一个 UNIT |
| **依赖最小** | 尽量减少 UNIT 间的依赖 | 每个 UNIT 都依赖其他 3 个 |

## 3. 规则写作标准

### 3.1 规则锚点格式

```markdown
### 规则 N：[标题]
**描述**: [规则描述——精确、无歧义、可翻译为代码逻辑]
- 正例：[输入] → [期望输出]
- 反例：[输入] → [期望错误]
- 边界：[边界条件] → [期望行为]
```

### 3.2 规则质量清单

| 检查项 | 要求 |
|--------|------|
| 描述是否精确 | 可翻译为 if/else 或 assert |
| 正例是否充分 | ≥ 1 个，覆盖主要场景 |
| 反例是否充分 | ≥ 1 个，覆盖主要异常 |
| 边界是否覆盖 | 最小值、最大值、空值、特殊字符 |
| 是否可验证 | 禁止模糊词（"正常"、"合理"、"友好"） |

### 3.3 排除项标准

好的排除项：
- "不做邮箱可达性验证" — 是合理需求但明确排除
- "不支持批量导入" — 是合理需求但明确排除

坏的排除项：
- "系统不应崩溃" — 否定句，不是排除项
- "不做非法操作" — 太模糊

## 4. 认知偏差对抗

| 偏差 | 表现 | 对抗 |
|------|------|------|
| **需求镀金** | 加入用户未提及的功能 | 严格对照用户原始描述，未提及的不加 |
| **技术驱动** | 先想技术方案再定需求 | 先完成业务分析，规则中不含技术实现 |
| **乐观偏差** | 只想正常路径，忽略异常 | 强制先写反例和边界，再写正例 |
| **范围蔓延** | 讨论过程中不断加需求 | 新增需求放排除项或标注"V2" |
| **假设遗漏** | 未暴露隐含假设 | 每条规则自问"还有什么我假设了但没说的？" |
