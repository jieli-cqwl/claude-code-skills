# 反模式与 TDD 验证手册

> 被 new-skills 主文件引用。包含 Skill 创建的常见反模式、Agent 合理化借口反制方法、TDD 验证细节。

---

## 1. 八种常见反模式

| # | 反模式 | 表现 | 正确做法 |
|---|--------|------|---------|
| 1 | **身份单薄** | "你是代码审查者" 一句话身份 | 补充心理驱动 + 质量锚点（三要素） |
| 2 | **约束后置** | 约束埋在文档中间或末尾 | 约束紧跟角色身份，放文档前部 |
| 3 | **缺少反例** | 只有好的 Few-shot，没有坏的 | 好/坏成对，坏的附"为什么坏" |
| 4 | **模糊输出** | "输出分析报告" 无具体格式 | 提供完整输出模板，含所有必填字段 |
| 5 | **知识散落** | 方法论混在入口 Skill 中 | 三层分离：入口驱动 + Agent 身份 + 知识引用 |
| 6 | **任务类型错配** | 创造型任务用竞争框架 | 按任务类型-身份匹配表选择身份深度 |
| 7 | **无偏差对抗** | 审查/验证类 Skill 缺少偏差检测 | 在输出前增加偏差自检环节 |
| 8 | **过长无结构** | 大段文字没有层次 | 用标题/表格/列表组织，遵循位置优化布局 |

### 新增反模式（来自官方标准 + superpowers）

| # | 反模式 | 表现 | 正确做法 |
|---|--------|------|---------|
| 9 | **CSO 违反** | description 写了完整摘要 | description 只写"何时触发"（CSO 原则） |
| 10 | **Token 超标** | SKILL.md 500+ 行，不拆分 | 详细内容拆到 references/ 按需加载 |
| 11 | **字段格式过时** | 用 `user_invocable`（下划线） | 用 `user-invocable`（连字符，官方标准） |
| 12 | **冗余字段** | 写了 `command: xxx` | `command` 已废弃，由 `name` 自动决定 |
| 13 | **无基线测试** | Skill 写完直接用，没验证 | 跑 TDD RED-GREEN-REFACTOR 验证 |

## 2. Agent 合理化借口反制（来自 superpowers）

### 什么是合理化借口

Agent 在执行 Skill 时，可能编造看似合理的理由跳过某些要求。例如：

- "这个场景不需要 Few-shot 示例，因为任务足够简单"
- "认知偏差对抗在这里不适用"
- "输出格式可以灵活处理，不必严格遵循模板"
- "这个步骤太繁琐，直接跳到下一步更高效"

这些借口表面合理，但实质是 Agent 在简化自己的工作。

### 反合理化表格方法

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1. 观察 | 让 Agent 执行 Skill，记录它跳过的步骤 | 不要纠正，先记录 |
| 2. 记录 | 将 Agent 给出的跳过理由记入表格 | 原文记录，不要改写 |
| 3. 反制 | 在 Skill 中添加针对性条款 | 用 FORBIDDEN + 具体借口 |
| 4. 验证 | 重新执行，确认 Agent 不再跳过 | 反复迭代直到稳定 |

### 反合理化表格模板

```markdown
## 反合理化条款

以下借口是 FORBIDDEN 的跳过理由：

| Agent 可能的借口 | 为什么这是借口 | 正确行为 |
|----------------|--------------|---------|
| "这个场景太简单，不需要 X" | 简单场景更需要 X 防止遗漏 | 执行 X |
| "已经隐式覆盖了 Y" | 隐式 ≠ 显式，必须明确输出 | 显式执行 Y |
| "Z 步骤在这里不适用" | 除非有明确排除条件，否则适用 | 执行 Z 或说明排除条件 |
```

### 实际示例

Skill 中的反合理化条款：

```markdown
FORBIDDEN 以下跳过理由：
- Do NOT 以"任务简单"为由跳过 Few-shot 对比示例
- Do NOT 以"不适用"为由跳过认知偏差自检（除非 Skill 类型为纯 Reference）
- Do NOT 以"格式灵活"为由省略输出模板的必填字段
- Do NOT 以"效率优先"为由合并或跳过验证步骤
```

## 3. TDD 验证详细流程

### RED 阶段：建立基线

**目的**：记录没有 Skill 时 Agent 的自然表现，作为改进的参照。

**操作**：
1. 准备一个代表性任务（Skill 要解决的核心场景）
2. 不加载任何 Skill，让 Agent 直接执行
3. 记录 Agent 的输出，标注以下维度：
   - 遗漏了哪些步骤
   - 输出格式是否符合预期
   - 是否出现认知偏差
   - 质量评分（1-5）

**记录模板**：
```markdown
### RED 基线记录

**任务**：[描述]
**日期**：[YYYY-MM-DD]
**无 Skill 输出摘要**：
- 遗漏步骤：[列表]
- 格式问题：[列表]
- 偏差表现：[列表]
- 质量评分：[1-5]
```

### GREEN 阶段：验证 Skill 有效

**目的**：加载 Skill 后，Agent 应达到预期质量标准。

**操作**：
1. 加载 Skill
2. 用相同任务让 Agent 再次执行
3. 对比 RED 基线，确认改进：
   - 遗漏步骤是否被补全
   - 输出格式是否符合模板
   - 偏差是否被对抗
   - 质量评分是否显著提升（目标 ≥4）

**REQUIRED**：GREEN 阶段质量评分必须 ≥ RED 阶段 + 2 分（或 RED 已 ≥3 时达到 5 分）

### REFACTOR 阶段：堵住漏洞

**目的**：识别 Agent 的合理化借口，迭代加固 Skill。

**操作**：
1. 仔细审查 GREEN 阶段的输出
2. 找出 Agent 虽然执行了但质量不足的步骤
3. 找出 Agent 给出合理化借口跳过的步骤
4. 更新反合理化表格（见 §2）
5. 在 Skill 中添加反制条款
6. 重新执行 GREEN 验证
7. 重复直到无新的合理化借口出现

**完成标准**：
- 连续 2 次执行无新的合理化借口
- 质量评分稳定 ≥4
- 所有 RED 阶段发现的问题都已被 Skill 覆盖
