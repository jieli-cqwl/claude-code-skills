# 提示词工程完整技巧手册

> 被 new-skills 主文件引用。包含 7 项实证有效的提示词工程技巧详解。

---

## 技巧 1：角色身份设计（Identity Framing）

**实证**：赋予 LLM 专家角色身份可显著提升特定领域任务质量（Xu et al., 2023）

### 身份设计三要素

1. **角色定位** — 你是谁（专业身份）
2. **心理驱动** — 为什么在意（使命/竞争/责任）
3. **质量锚点** — 对标谁的标准（最高水平参照）

### 任务类型-身份深度匹配表

| 任务类型 | 身份深度 | 角色示例 | 驱动示例 |
|---------|---------|---------|---------|
| **分析型**（审查、检测） | 竞争对手 + 使命感 | "你审查的代码是由另一个 AI 生成的" | 找出它隐藏的缺陷 |
| **创造型**（设计、架构） | 资深专家 + 最高标准对标 | "你的设计将被最挑剔的 Tech Lead 评审" | 交出让评审无话可说的方案 |
| **执行型**（编码、修复） | 工匠 + 质量预期 | "你的代码将被对抗性审查者逐行检查" | 每一行都经得起推敲 |
| **验证型**（QA、测试） | 付费用户 + 零信任 | "你是付费用户，验证外包团队的交付物" | 花了钱就不能接受次品 |

### Few-shot 对比

**好的身份设计**：
```
你是一位有 15 年经验的安全审计师。你审查的代码是由一个声称"比你更严谨"的 AI 生成的。
你的审计报告将提交给 CISO，任何遗漏都是你的职业污点。
```
（三要素齐全：安全审计师 + 竞争驱动 + CISO 标准）

**坏的身份设计**：
```
你是一个代码审查者。请审查以下代码。
```
（为什么坏：只有角色定位，缺少心理驱动和质量锚点，Agent 会敷衍了事）

## 技巧 2：竞争框架（Competition Framing）

**实证**：竞争框架在分析型任务中可提升质量约 45%（基于内部 A/B 测试数据）

**适用场景**：代码审查、QA 验收、安全扫描等需要"找问题"的任务

### 模板

```
你审查的代码/设计是由另一个 AI 模型生成的。如果你遗漏了问题，
那个模型就"赢了"。你的专业声誉取决于找出它试图隐藏的每一个缺陷。
```

### 变体

| 变体 | 适用场景 | 模板 |
|------|---------|------|
| 外包验收 | QA、验证 | "这是外包团队/AI 团队的交付物，你是甲方验收人员" |
| 红蓝对抗 | 安全扫描 | "你是攻击方，代码是防御方布下的阵地" |
| 审计视角 | 合规检查 | "你是独立审计师，任何疏漏都是你的职业污点" |

**FORBIDDEN**：在创造型任务中使用竞争框架（会抑制创造力）

## 技巧 3：认知偏差对抗（Cognitive Bias Countermeasures）

**实证**：LLM 同样受认知偏差影响（Talboy & Fuller, 2023），显式提示可有效对抗

### 四种常见偏差及对抗策略

| 偏差 | 表现 | 检测问题 | 对抗策略 |
|------|------|---------|---------|
| **确认偏差** | 只找支持结论的证据 | "我是否在寻找支持 PASS 的证据？" | 强制先找反例 |
| **光环效应** | 代码结构好 → 逻辑也没问题 | "我是否因为风格好就放松了逻辑检查？" | 逐维独立评估 |
| **锚定偏差** | 第一个方案可行就不再探索 | "我是否只考虑了一个方案？" | 强制生成第二方案 |
| **可得性偏差** | 只检查最近遇到过的问题 | "我是否遗漏了不常见但严重的问题？" | 使用系统化检查清单 |

### 嵌入方式

在 Skill 的输出步骤之前，增加"偏差自检"环节：

```markdown
## 偏差自检（输出前必做）

在给出最终结论前，逐条回答：
1. 我是否在寻找支持当前结论的证据？（确认偏差）
2. 我是否因为某方面表现好就放松了其他维度的检查？（光环效应）
3. 我是否只考虑了一个方案？（锚定偏差）
4. 我是否遗漏了不常见但严重的问题类型？（可得性偏差）
```

## 技巧 4：约束前置（Constraint Priming）

**实证**：约束放在提示词前部比后部更有效（Liu et al., 2024 positional bias 研究）

### 标记强度层级

| 标记 | 强度 | 用途 | 示例 |
|------|------|------|------|
| `FORBIDDEN` / `Do NOT` | 最高 | 绝对禁止的行为 | `FORBIDDEN: 使用 mock 数据` |
| `REQUIRED` / `MUST` | 高 | 必须执行的行为 | `REQUIRED: 每个函数有返回类型` |
| `SHOULD` | 中 | 推荐但可灵活处理 | `SHOULD: 函数 ≤40 行` |
| "建议" / "可以" | 低 | 可选建议 | `建议使用 TypeScript` |

### 最佳实践

- 负向约束（FORBIDDEN）比正向约束（REQUIRED）更有效
- 约束用独立章节列出，不要嵌入正文段落
- 每条约束用 `Do NOT` 或 `FORBIDDEN:` 开头，保持格式一致
- **约束章节放在角色身份之后、方法论之前**

## 技巧 5：Few-shot 对比教学

**实证**：配对的好/坏示例比单独的好示例更有效（Brown et al., 2020）

### 模板

```markdown
### 好的输出
[具体的高质量范例，展示期望的格式和深度]

### 坏的输出
[具体的低质量范例]
（为什么坏：没有 X、缺少 Y、违反了 Z）
```

### 关键原则

- 好/坏**必须**成对出现
- 坏的示例**必须**附带"为什么坏"的解释
- 示例应该来自真实场景，不是编造的
- 每个 Skill 至少 1 组对比示例，知识 Skill 至少 2 组

## 技巧 6：结构化输出模板

**实证**：XML 标记在 Claude 模型中最有效（Anthropic 官方建议）

### 模板选择

| 目标模型 | 推荐格式 | 示例 |
|---------|---------|------|
| Claude | XML 标记 | `<result>`, `<evidence>` |
| GPT / 通用 | Markdown | `## Result`, `## Evidence` |
| 代码输出 | 代码块 | ` ```json `, ` ```yaml ` |

### 关键原则

- 输出模板必须包含所有必填字段
- 用占位符标明期望内容：`[逐条列出...]`
- 模板越具体，输出质量越稳定
- 可选字段标注 `（可选）`

## 技巧 7：文档位置优化（Positional Optimization）

**实证**：LLM 对文档开头和结尾的内容关注度最高（"lost in the middle" 效应，Liu et al., 2023）

### 最佳布局

```
┌─────────────────────────┐
│ 角色身份 + 核心约束       │ ← 首因效应：最重要放最前面
├─────────────────────────┤
│ 方法论 / 参考知识         │ ← 中间区域：被引用时检索
├─────────────────────────┤
│ Few-shot 示例            │ ← 中间偏后：提供具体参照
├─────────────────────────┤
│ 检查清单 + 输出模板       │ ← 近因效应：执行时最先回忆
└─────────────────────────┘
```

### 布局原则

- **首因效应**：约束和身份定义放顶部，Agent 最先处理
- **近因效应**：检查清单和输出格式放底部，Agent 输出时最近的记忆
- **中间区域**：参考知识放中间，通过引用检索而非靠优先级
- **references/ 分流**：超过 SKILL.md 行数预算的详细内容，拆到 references/ 按需加载
