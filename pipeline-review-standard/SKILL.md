# Review Standard - 审查标准

> 引用者：pipeline-checker（主用）、pipeline-planner（引用，用于 Design 评审）

---

## 1. 对抗性审查思维（Adversarial Mindset）

审查的本质是**找问题**，不是**证明没问题**。

### 核心原则

- **有罪推定**：假设代码有漏洞，你的任务是找到它
- **不信任自证**：开发者说"测试通过"，你自己再验一遍
- **假设最坏情况**：每个输入都可能是恶意的，每个路径都可能出错
- **禁止橡皮图章**：不允许"看起来没问题"的模糊结论

### 橡皮图章检测标准

以下输出视为无效审查（橡皮图章），必须重做：

- "代码结构合理"（没有具体分析）
- "测试覆盖充分"（没有逐条核对）
- "整体质量良好"（没有客观证据）
- "没有发现明显问题"（没有说明检查了什么）
- 任何不附带文件路径:行号的结论

## 2. Design 评审标准

Planner 在制定计划前，先评审 Design 文档。

### 判定标准

| 结果 | 含义 |
|------|------|
| `DESIGN_OK` | 设计可执行，可以开始制定计划 |
| `DESIGN_ISSUE` | 设计存在问题，需要修正后重新评审 |

### 评审检查项

| # | 检查项 | DESIGN_ISSUE 触发条件 |
|---|--------|---------------------|
| 1 | clarify 规则覆盖 | 存在规则无对应接口/数据模型 |
| 2 | 接口完整性 | 缺少错误场景、参数校验 |
| 3 | 可执行性 | 模块边界模糊到无法拆分任务 |
| 4 | 过度设计 | 引入了 clarify 未要求的抽象层 |
| 5 | 数据模型 | 无法支撑所有 clarify 正例的数据流 |

### 评审输出格式

```markdown
REVIEW: DESIGN_OK

## 评审摘要
- 共检查 N 条 clarify 规则，全部有对应设计
- 接口定义完整，含错误场景
- 无过度设计

## 检查明细
[逐项列出检查结果]
```

或：

```markdown
REVIEW: DESIGN_ISSUE

## Issues
1. [ISSUE-1] clarify R3 "密码长度>=8" 无对应校验接口
   - 位置：handoff_design.md 接口清单
   - 建议：POST /users 入参增加 password 校验规则

2. [ISSUE-2] UserModel 缺少 email 唯一性约束
   - 位置：数据模型部分
   - 建议：增加 unique=True 约束

## 检查明细
[逐项列出检查结果]
```

### Design 评审自检清单

1. [ ] 是否逐条核对了 clarify 规则与 design 接口的对应关系？
2. [ ] 是否以"能否拆分为可执行任务"的视角审视设计粒度？
3. [ ] DESIGN_ISSUE 是否给出了具体位置和修改建议（而非"不够完善"）？

## 3. Plan 评审标准

Implementer 在执行前，先评审 Plan 文档。

### 判定标准

| 结果 | 含义 |
|------|------|
| `PLAN_OK` | 计划可执行，可以开始实现 |
| `PLAN_ISSUE` | 计划存在问题，需要修正后重新评审 |

### 评审检查项

| # | 检查项 | PLAN_ISSUE 触发条件 |
|---|--------|-------------------|
| 1 | 文件路径验证 | 引用路径不存在（Glob 验证） |
| 2 | AC 可测性 | 无法翻译为 assert |
| 3 | 依赖拓扑 | 存在循环或顺序矛盾 |
| 4 | 任务粒度 | 单任务改动 > 5 文件 |
| 5 | 设计一致性 | 与 handoff_design.md 矛盾 |

### 评审输出格式

```markdown
REVIEW: PLAN_OK

## 评审摘要
- 共 N 个 Task，M 条 AC
- 文件路径全部通过 Glob 验证
- AC 全部可翻译为 assert
- 依赖无循环

## 检查明细
[逐项列出检查结果]
```

或：

```markdown
REVIEW: PLAN_ISSUE

## Issues
1. [ISSUE-1] Task-2 依赖 Task-3 但排在 Task-3 前面
   - 类型：依赖拓扑
   - 建议：调整 Task-2 和 Task-3 顺序

2. [ISSUE-2] Task-1 AC2 "界面友好" 无法翻译为 assert
   - 类型：AC 可测性
   - 建议：改为 "错误提示包含字段名和限制条件"

## 检查明细
[逐项列出检查结果]
```

### Plan 评审自检清单

1. [ ] 是否逐条核对了每个任务的文件路径是否真实存在（通过 Glob 验证）？
2. [ ] 是否以"能否翻译为 assert"的视角审视每个 AC？
3. [ ] PLAN_ISSUE 是否给出了具体位置和修改建议（而非"不够完善"）？

## 4. 评审通用规范

### 输出格式要求

评审输出第一行必须是以下格式之一：
```
REVIEW: DESIGN_OK
REVIEW: DESIGN_ISSUE
REVIEW: PLAN_OK
REVIEW: PLAN_ISSUE
```

### Issue 格式要求

每个 Issue 必须包含：
- **编号**：`[ISSUE-N]`
- **描述**：具体问题是什么
- **位置**：在哪个文件/章节发现
- **建议**：具体的修改建议

### 禁止行为

- 禁止"看起来没问题"的模糊结论
- 禁止不给修改建议的 ISSUE
- 禁止跳过任何检查项
- 禁止在未完成全部检查的情况下给出 OK

## 5. Few-shot 对比示例

### 好的评审输出

```
REVIEW: DESIGN_ISSUE

## Issues
1. [ISSUE-1] clarify R3 规定"密码长度>=8"，但 POST /users 接口入参
   未定义 password 校验规则
   - 位置：handoff_design.md 第 3.2 节接口清单
   - 建议：入参增加 password(str, min_length=8)，错误码 WEAK_PASSWORD

2. [ISSUE-2] 接口 GET /users/{id} 缺少 404 错误场景
   - 位置：handoff_design.md 第 3.3 节
   - 建议：增加 404 {"error_code": "USER_NOT_FOUND"}

## 检查明细
| # | 检查项 | 结果 | 说明 |
|---|--------|------|------|
| 1 | clarify 覆盖 | ISSUE | R3 无对应校验 |
| 2 | 接口完整性 | ISSUE | GET /users/{id} 缺 404 |
| 3 | 可执行性 | OK | 模块边界清晰 |
| 4 | 过度设计 | OK | 无多余抽象 |
| 5 | 数据模型 | OK | 支撑全部正例 |
```

### 坏的评审输出

```
设计文档结构清晰，接口定义基本完整。建议补充一些错误处理。DESIGN_OK
（模糊结论、未逐项检查、有 Issue 却给了 OK）
```

## 6. 检查清单

审查完成前必须确认：

1. [ ] 是否采用了对抗性思维（找问题而非证明没问题）？
2. [ ] 是否逐项完成了所有检查项？
3. [ ] 每个 ISSUE 是否有具体位置和修改建议？
4. [ ] 是否存在橡皮图章式的模糊结论？
5. [ ] 评审输出第一行是否为标准格式（REVIEW: XXX）？
6. [ ] OK 结论是否在全部检查项通过后才给出？
