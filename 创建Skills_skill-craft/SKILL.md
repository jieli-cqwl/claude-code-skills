# Skill Craft - 高质量 Skill 创建指南

> ultrathink
>
> 本 Skill 教你如何创建高质量的 Skills。包含三种类型模板、7 项实证有效的提示词工程技巧、质量自检清单和常见反模式。

---

## 1. 三种 Skill 类型及最佳结构

### 类型 A：入口 Skill（`context: fork`）

**职责**：Task prompt — 驱动 SubAgent 的任务指令

**最佳结构**：

```markdown
---
name: xxx
description: 一句话描述
context: fork
agent: pipeline-xxx
user-invocable: true
trigger: /xxx
---

# 前置条件检查
[列出必须存在的输入文件/状态]

# 执行流程
[SubAgent 的具体任务步骤，精确到可执行]

# 输出格式
[明确输出文件路径和内容结构]

# 完成标准
[可验证的完成条件]
```

**关键原则**：
- 入口 Skill 只负责"驱动"，不包含领域知识
- 领域知识放在知识 Skill 中，由 SubAgent 的 `skills` 字段引用
- 执行流程必须精确到 SubAgent 可以无歧义执行

### 类型 B：知识 Skill（`user-invocable: false`）

**职责**：Reference material — 领域知识、方法论、检查清单

**最佳结构**：

```markdown
---
name: xxx
description: 一句话描述
user-invocable: false
---

# [领域名] - [主题]

> 引用者：列出哪些 agent/skill 会加载此知识

## 1. 核心原则/框架
[方法论、原则、思维模型]

## 2. 量化标准
[可测量的质量标准，表格形式]

## 3. 执行清单
[逐步操作指南]

## 4. Few-shot 对比示例
### 好的输出
[具体的高质量范例]

### 坏的输出
[具体的低质量范例 + 为什么坏]

## 5. 检查清单
[完成前的自检项]

## 6. 常见反模式
[表格：反模式 | 表现 | 正确做法]
```

**关键原则**：
- 知识 Skill 是"被引用"的，不直接面向用户
- 必须有 Few-shot 对比示例（好/坏成对）
- 必须有检查清单和反模式

### 类型 C：独立 Skill（主对话直接使用）

**职责**：在主对话中直接执行的功能

**最佳结构**：

```markdown
---
name: xxx
description: 一句话描述
user-invocable: true
trigger: /xxx
---

# [Skill 名]

> [适用场景描述]

## 执行流程
[步骤化的操作指南]

## 约束
[FORBIDDEN/REQUIRED 标记的硬约束]

## 输出格式
[明确的输出模板]
```

## 2. 七项提示词工程核心技巧

### 技巧 1：角色身份设计（Identity Framing）

**实证**：赋予 LLM 专家角色身份可显著提升特定领域任务质量（Xu et al., 2023）

**认知任务匹配规则**：

| 任务类型 | 身份深度 | 示例 |
|---------|---------|------|
| **分析型**（审查、检测） | 竞争对手 + 使命感 | "你审查的代码是由另一个 AI 生成的" |
| **创造型**（设计、架构） | 资深专家 + 最高标准对标 | "你的设计将被最挑剔的 Tech Lead 评审" |
| **执行型**（编码、修复） | 工匠 + 质量预期 | "你的代码将被对抗性审查者逐行检查" |
| **验证型**（QA、测试） | 付费用户 + 零信任 | "你是付费用户，验证外包团队的交付物" |

**身份设计三要素**：
1. **角色定位**：你是谁（专业身份）
2. **心理驱动**：为什么在意（使命/竞争/责任）
3. **质量锚点**：对标谁的标准（最高水平参照）

**反模式**：
- 只写"你是 X"，缺少心理驱动维度
- 身份与任务类型不匹配（如分析型任务用创造型身份）

### 技巧 2：竞争框架（Competition Framing）

**实证**：竞争框架在分析型任务中可提升质量约 45%（基于内部 A/B 测试数据）

**适用场景**：代码审查、QA 验收、安全扫描等需要"找问题"的任务

**模板**：
```
你审查的代码/设计是由另一个 AI 模型生成的。如果你遗漏了问题，
那个模型就"赢了"。你的专业声誉取决于找出它试图隐藏的每一个缺陷。
```

**变体**：
- **外包验收**："这是外包团队/AI 团队的交付物，你是甲方验收人员"
- **红蓝对抗**："你是攻击方，代码是防御方布下的阵地"
- **审计视角**："你是独立审计师，任何疏漏都是你的职业污点"

**FORBIDDEN**：在创造型任务中使用竞争框架（会抑制创造力）

### 技巧 3：认知偏差对抗（Cognitive Bias Countermeasures）

**实证**：LLM 同样受认知偏差影响（Talboy & Fuller, 2023），显式提示可有效对抗

**四种常见偏差及检测清单**：

| 偏差 | 表现 | 检测问题 | 对抗策略 |
|------|------|---------|---------|
| **确认偏差** | 只找支持结论的证据 | "我是否在寻找支持 PASS 的证据？" | 强制先找反例 |
| **光环效应** | 代码结构好 → 逻辑也没问题 | "我是否因为代码风格好就放松了逻辑检查？" | 逐维独立评估 |
| **锚定偏差** | 第一个方案看起来可行就不再探索 | "我是否只考虑了一个方案？" | 强制生成第二方案 |
| **可得性偏差** | 只检查最近遇到过的问题类型 | "我是否遗漏了不常见但严重的问题？" | 使用系统化检查清单 |

**嵌入位置**：放在输出步骤之前，作为"偏差自检"环节

### 技巧 4：约束前置（Constraint Priming）

**实证**：约束放在提示词前部比后部更有效（Liu et al., 2024 positional bias 研究）

**标记强度层级**：

| 标记 | 强度 | 用途 |
|------|------|------|
| `FORBIDDEN` / `Do NOT` | 最高 | 绝对禁止的行为 |
| `REQUIRED` / `MUST` | 高 | 必须执行的行为 |
| `SHOULD` | 中 | 推荐但可灵活处理 |
| "建议" / "可以" | 低 | 可选建议 |

**最佳实践**：
- 负向约束（FORBIDDEN）比正向约束（REQUIRED）更有效
- 约束用独立章节列出，不要嵌入正文段落
- 每条约束用 `Do NOT` 开头，保持格式一致

### 技巧 5：Few-shot 对比教学

**实证**：配对的好/坏示例比单独的好示例更有效（Brown et al., 2020）

**模板**：
```markdown
### 好的输出
[具体的高质量范例，展示期望的格式和深度]

### 坏的输出
[具体的低质量范例]
（[解释为什么坏：没有 X、缺少 Y、违反了 Z]）
```

**关键原则**：
- 好/坏必须成对出现
- 坏的示例必须附带"为什么坏"的解释
- 示例应该来自真实场景，不是编造的

### 技巧 6：结构化输出模板

**实证**：XML 标记在 Claude 模型中最有效（Anthropic 官方建议）

**模板选择**：

| 目标模型 | 推荐格式 | 示例 |
|---------|---------|------|
| Claude | XML 标记 | `<result>`, `<evidence>` |
| GPT / 通用 | Markdown | `## Result`, `## Evidence` |
| 代码输出 | 代码块 | ` ```json `, ` ```yaml ` |

**关键原则**：
- 输出模板必须包含所有必填字段
- 用占位符标明期望内容：`[逐条列出...]`
- 模板越具体，输出质量越稳定

### 技巧 7：文档位置优化（Positional Optimization）

**实证**：LLM 对文档开头和结尾的内容关注度最高（"lost in the middle" 效应，Liu et al., 2023）

**最佳布局**：

```
┌─────────────────────────┐
│ 角色身份 + 核心约束       │ ← 最重要，放最前面
├─────────────────────────┤
│ 方法论 / 参考知识         │ ← 中间区域
├─────────────────────────┤
│ Few-shot 示例            │ ← 中间偏后
├─────────────────────────┤
│ 检查清单 + 输出模板       │ ← 放最后，执行时最先回忆
└─────────────────────────┘
```

**关键原则**：
- 约束和身份定义放顶部（首因效应）
- 检查清单和输出格式放底部（近因效应）
- 参考知识放中间（被引用时检索，不需要高优先级）

## 3. Skill 质量自检清单

创建完 Skill 后，逐项检查：

### 结构完整性

- [ ] frontmatter 是否包含 `name`, `description`, `user-invocable`？
- [ ] 入口 Skill 是否有 `context: fork` + `agent` 字段？
- [ ] 知识 Skill 是否标注了引用者（`> 引用者：...`）？
- [ ] 是否有 Few-shot 对比示例（好/坏成对）？
- [ ] 是否有检查清单？
- [ ] 是否有反模式列表？

### 提示词工程质量

- [ ] 角色身份是否包含三要素（角色定位 + 心理驱动 + 质量锚点）？
- [ ] 约束是否前置且用 `FORBIDDEN` / `Do NOT` 格式？
- [ ] 分析型任务是否使用了竞争框架？
- [ ] 是否有认知偏差对抗清单（至少 3 种偏差）？
- [ ] 文档布局是否遵循位置优化原则（约束在前，清单在后）？

### 可执行性

- [ ] 每个步骤是否足够具体，AI Agent 可无歧义执行？
- [ ] 输出格式是否有明确模板（不是"输出分析结果"这种模糊描述）？
- [ ] 量化标准是否有具体数值（不是"代码质量良好"这种主观描述）？

### 注册完整性

- [ ] 是否在 `skills/STANDARD.md` 中注册？
- [ ] STANDARD.md 中的描述是否与 Skill 一致？
- [ ] 如果是入口 Skill，对应的 SubAgent 是否存在？

## 4. 常见反模式

| # | 反模式 | 表现 | 正确做法 |
|---|--------|------|---------|
| 1 | **身份单薄** | "你是代码审查者" 一句话身份 | 加入心理驱动 + 质量锚点 |
| 2 | **约束后置** | 约束埋在文档中间或末尾 | 约束紧跟角色身份，放在文档前部 |
| 3 | **缺少反例** | 只有好的 Few-shot，没有坏的 | 好/坏成对，坏的附解释 |
| 4 | **模糊输出** | "输出分析报告" 无具体格式 | 提供完整输出模板，含所有必填字段 |
| 5 | **知识散落** | 方法论混在入口 Skill 中 | 三层分离：入口驱动 + Agent 身份 + 知识引用 |
| 6 | **任务类型错配** | 创造型任务用竞争框架 | 按认知任务匹配表选择身份深度 |
| 7 | **无偏差对抗** | 审查/验证类 Skill 缺少偏差检测 | 在输出前增加偏差自检环节 |
| 8 | **过长无结构** | 大段文字没有层次 | 用标题、表格、列表组织，遵循位置优化 |

## 5. STANDARD.md 注册指南

新 Skill 创建后，必须在 `~/.claude/skills/STANDARD.md` 中注册。

### 入口 Skill 注册模板

在 `## Skills 详情` 中追加：

```markdown
### N. xxx（中文名）

**触发**：`/xxx`

**用途**：一句话描述

**版本**：v1.0（日期）

**核心产出**：
- [产出列表]

**前置条件**：[依赖什么]
```

同时在 `## 快速选择` 表格中追加一行。

### 知识 Skill 注册

知识 Skill 不在 STANDARD.md 的 Skills 详情中注册（因为用户不直接使用），但需要在引用它的 SubAgent 的 `skills` 字段中声明。

### 独立 Skill 注册

同入口 Skill，在 STANDARD.md 中注册触发命令和描述。

## 执行流程

当用户触发 `/skill-craft` 时：

1. **确认 Skill 类型**：询问用户要创建的是入口 Skill、知识 Skill 还是独立 Skill
2. **收集信息**：Skill 名称、用途、目标任务类型（分析/创造/执行/验证）
3. **选择技巧组合**：根据任务类型从 7 项技巧中选择 3-5 项最相关的
4. **生成 Skill 文件**：使用对应类型的模板 + 选中的技巧
5. **质量自检**：对照自检清单逐项验证
6. **注册**：在 STANDARD.md 中注册（如果是用户可调用的）
7. **输出**：展示创建的文件路径和自检结果
