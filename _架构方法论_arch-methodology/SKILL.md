# Architecture - 架构设计方法论

> 引用者：pipeline-designer（主用）、pipeline-planner（引用）

---

## 1. 核心方法论：先扫描再设计

架构设计必须基于现有代码的真实状态，禁止凭空设计。

### 扫描流程

1. **项目结构扫描**：使用 Glob 了解目录结构、技术栈、框架版本
2. **现有模式识别**：使用 Grep 搜索现有路由/模型/服务的命名和组织方式
3. **风格一致性分析**：记录现有代码中的命名约定、错误处理模式、数据访问模式
4. **依赖分析**：检查 package.json / requirements.txt / go.mod 了解已有依赖

### 扫描产出

扫描结果必须体现在 Handoff 的"输入分析"部分：
- 项目使用的技术栈和框架版本
- 现有模块数量和组织方式
- 已有的命名约定和编码模式
- 与当前需求相关的现有代码位置

## 2. 多方案对比方法论（Tree of Thoughts）

关键架构决策必须列出 2-3 个备选方案并对比，禁止直接给出"唯一正确答案"。

### 对比维度（至少包含）

| 维度 | 说明 |
|------|------|
| 实现复杂度 | 开发工作量、学习成本 |
| 与现有代码一致性 | 是否与项目已有模式匹配 |
| 可维护性 | 长期维护成本、可扩展性 |

### 对比格式

```markdown
### [决策标题] 方案对比

| 维度 | 方案 A: [名称] | 方案 B: [名称] | 方案 C: [名称] |
|------|---------------|---------------|---------------|
| 与现有代码一致性 | [具体描述] | [具体描述] | [具体描述] |
| 实现复杂度 | [低/中/高] | [低/中/高] | [低/中/高] |
| 可维护性 | [具体描述] | [具体描述] | [具体描述] |

**选择**: 方案 X，理由：[1-2 句话核心理由]
```

### 判断哪些是"关键决策"

- 技术栈选择（数据库、框架、第三方服务）
- 架构模式（单体/微服务、同步/异步、RESTful/GraphQL）
- 数据模型核心结构
- 认证/授权方案
- 缓存策略

## 3. 接口定义完整性标准

每个接口必须完整定义以下内容：

### 入参规范

- 参数名称和类型
- 参数校验规则（长度、范围、格式、必填/可选）
- 校验失败的错误响应

### 出参规范

- 成功响应格式和字段
- 失败响应格式和错误码
- 边界情况的响应

### 错误码体系

- 每个接口至少定义：参数校验错误、业务逻辑错误、系统错误
- 错误码命名有统一前缀或分类
- 错误消息面向用户（不暴露技术细节）

---

## 4. 模块边界设计原则

每个模块必须明确定义：

### "负责什么"

- 模块的核心职责（1-3 句话概括）
- 对外暴露的接口清单
- 管理的数据/状态范围

### "不负责什么"

- 明确排除的职责
- 不处理的边界情况（由哪个模块处理）
- 不直接访问的外部资源

---

## 5. 设计可追溯性

每个设计产出必须能追溯到需求来源。

### 覆盖表格式

```markdown
| clarify 规则 | 对应接口/模块 | 覆盖状态 |
|-------------|-------------|---------|
| R1: [规则描述] | POST /api/v1/xxx | 已覆盖 |
| R2: [规则描述] | UserModel.validate() | 已覆盖 |
| E1: [排除项] | 不设计 | 已确认排除 |
```

如有规则无对应设计产出，必须停下来补充，不能输出不完整的设计。

## 6. Key Decisions 输出规范

除 handoff_design.md 外，还需输出 Key_Decisions.md，采用 MADR 精简版格式。

### 双层结构

- **第一层（概要表）**：人扫描表格总览所有决策方向
- **第二层（详细记录）**：每条决策展开背景、选项对比、妥协和影响

### 每条决策必含字段

| 字段 | 说明 |
|------|------|
| 状态 | Proposed / Accepted / Rejected |
| 影响度 | High（架构级）/ Medium（模块级）/ Low（局部实现） |
| 背景 | 为什么需要做这个决策 |
| 选项表 | 至少 2 个备选方案，含优缺点 |
| 决策 | 选择了哪个方案 |
| 理由 | 选择的核心理由 |
| 接受的妥协 | 选择此方案放弃或延迟了什么 |
| 影响 | 对后续步骤（Plan/Implement）的具体影响 |

## 7. Few-shot 对比示例

### 好的设计输出

```
输入分析：
- 扫描项目发现现有模型在 src/models/（SQLAlchemy ORM，5 个模型文件）
- API 风格：RESTful，路由在 src/api/v1/（文件路由模式，12 个路由文件）
- 认证：JWT（src/auth/jwt.py）
- 数据库：PostgreSQL，已有 alembic migration

决策：
- 路由方案选择文件路由（方案 A），因为与现有 12 个路由文件风格一致
- 数据模型复用现有 BaseModel，新增 username 字段（3-20 字符）和 email 字段（RFC 5322）

产出：
- POST /api/v1/users
  - 入参：username(str, 3-20字符), email(str, RFC5322), password(str, >=8字符)
  - 成功：201 {"id": int, "username": str, "created_at": datetime}
  - 失败：422 {"error_code": "VALIDATION_ERROR", "details": [...]}
  - 失败：409 {"error_code": "USER_EXISTS", "message": "用户名已存在"}
```

### 坏的设计输出

```
建议使用微服务架构。接口使用 RESTful 风格。
用户表包含必要字段。密码需要加密存储。
（没有扫描现有代码、没有方案对比、没有具体接口定义、没有错误场景）
```

## 8. 检查清单

设计完成前必须逐条确认：

1. [ ] clarify 每条规则都有对应接口或数据模型？（列出覆盖表）
2. [ ] 每个接口都定义了错误场景和错误码？
3. [ ] 扫描了现有代码并保持风格一致？
4. [ ] 关键决策给出了 2+ 备选方案对比？
5. [ ] 是否引入了 clarify 未提及的功能？（如是则删除）
6. [ ] 假设已标注为"待确认"？
7. [ ] 是否为每个关键架构决策生成了 Key_Decisions.md 条目？
8. [ ] 模块边界是否明确定义了"负责什么"和"不负责什么"？

## 9. 常见反模式

| 反模式 | 表现 | 正确做法 |
|--------|------|---------|
| 凭空设计 | 不看现有代码直接画架构 | 先 Glob/Grep 扫描，基于现有模式设计 |
| 只有正常路径 | 接口只定义成功场景 | 每个接口必须定义错误场景和错误码 |
| 过度设计 | 引入不必要的抽象层/设计模式 | 只解决需求中明确提到的问题 |
| 照搬模板 | 全是泛泛描述无具体内容 | 必须包含具体的接口定义和技术选型 |
| 单一方案 | 关键决策只给一个方案 | 至少 2 个备选方案对比 |
